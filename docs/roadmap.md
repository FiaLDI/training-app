# Дорожная карта развития (Roadmap) IronLog

В данном документе представлены стратегические направления и сценарии развития веб-трекера тренировок IronLog.

---

## 🎯 Сценарии развития (Векторы)

В зависимости от бизнес-целей и потребностей пользователей проект может развиваться по 4 основным направлениям:

1. Gym-First (Фокус на удобстве в зале): максимальное ускорение ввода данных с мобильных устройств, таймеры, вибро-отклики, PWA, минимизация отвлекающих факторов.
2. Coaching & Social (Фокус на тренерах и сообществе): связь «тренер — ученик», шеринг программ и тренировок по ссылкам, комментарии, видеоразборы.
3. Data & Progression (Фокус на научном подходе и аналитике): периодизация, расчеты 1RM, отслеживание RPE/RIR, умные рекомендации весов, графики мышечных объемов.
4. Enterprise & Platform (Фокус на масштабируемости и безопасности): полноценная мультиюзерная изоляция данных, интеграция с фитнес-трекерами (Apple Health, Garmin), масштабируемый бэкенд.

## 🗺 Комплексный поэтапный план (Phased Roadmap)

### Фаза 1: Фундамент, безопасность и стабилизация (Core & Security)
> Сроки: Краткосрочная перспектива  
> Цель: Устранить технический долг, защитить пользовательские данные и улучшить базовую навигацию.

* [x] Безопасная аутентификация по постоянному коду (без SMTP):
  * [x] Хранение только bcrypt-хеша login-кода в БД (`login_code_hash`); plaintext в БД и логах не допускается.
  * [x] Схема поиска: колонка-индекс `login_code_lookup` = HMAC-SHA256(`LOGIN_CODE_PEPPER`, code) + bcrypt для проверки. Длина кода 12.
  * [x] Админ-панель (`/admin/users`, пункт в «Ещё» только для admin): список `email | создан | последний вход` **без** кода; создание пользователя и сброс кода с одноразовым показом plaintext.
  * [x] `POST /auth/register` для нового аккаунта возвращает код **один раз** в ответе API; повторная регистрация существующего email код не раскрывает.
  * [x] Rate-limiting: по IP на login/register + по аккаунту на login (5 / 15 мин после HMAC-lookup).
  * [x] Инвалидация сессий при сбросе кода: Redis-cutoff + durable `sessions_revoked_at` в БД.
  * (Опционально позже) self-service OTP по email (SMTP / Resend) — только при росте публичной аудитории.
* [x] Строгая мультитенантность и изоляция данных (Data Isolation):
  * [x] Проверка всех модулей бэкенда (sources, exercises, templates, body-measurement, feedback).
  * [x] Разделение упражнений на «системные» (общие) и «пользовательские» (кастомные).
  * [x] Гарантия фильтрации по userId во всех SQL-запросах.
* [x] Инфраструктура разделяемого состояния (Redis):
  * [x] Сервис `redis:7-alpine` в `docker-compose.yml`; данные не персистентные (`--save ''`, `appendonly no`), `maxmemory` + `allkeys-lru`, бэкапы не требуются. `depends_on` намеренно `service_started`, а не `service_healthy` — Redis не должен блокировать деплой.
  * [x] Порт `CachePort` в `shared/cache/core/ports` + `RedisCacheAdapter` / `MemoryCacheAdapter` в `infrastructure`.
  * [x] **Graceful degradation**: при недоступности Redis адаптер переключается на in-memory, приложение не отдаёт 5xx. `increment` работает и в fallback — иначе rate-limiting молча открылся бы. Текущее состояние видно в `GET /api/health` (`cache: redis | memory-fallback`).
  * [x] Кеш профиля пользователя в `AuthGuard` (`auth:user:{id}`, TTL 300 с) — снимает `SELECT` пользователя с **каждого** авторизованного запроса. Login-код в кеш не попадает.
  * [x] Отзыв JWT: по одному токену (логаут) и сразу по всем сессиям пользователя через отсечку по `iat` — основа для инвалидации при сбросе кода.
  * [x] Rate-limiting по IP через `@RateLimit` + `RateLimitGuard` (`/auth/login` — 10/15 мин, `/auth/register` — 5/час), с `trust proxy` в `main.ts`. Устойчив к перезапуску контейнера при деплое.
  * [x] Прогрессивная блокировка **по аккаунту** на login (`rl:auth-login-user:{id}`, 5 / 15 мин) — после HMAC-lookup, до bcrypt-verify.
  * [x] Задел на горизонтальное масштабирование (сценарий 4 «Enterprise & Platform»), где общее хранилище становится обязательным.
  * Известные ограничения: (1) удалённый или разжалованный пользователь сохраняет доступ до истечения TTL кеша — нужна инвалидация `auth:user:{id}` при любом изменении профиля; (2) смена `LOGIN_CODE_PEPPER` инвалидирует все `login_code_lookup` — всем нужен сброс кода. Если миграция HashLoginCodes уже прошла без pepper в `.env`, она использовала `JWT_SECRET`: либо оставьте pepper пустым (тот же fallback), либо выставьте `LOGIN_CODE_PEPPER` равным тому `JWT_SECRET`.
* [x] Оптимизация навигации и роутинга:
  * [x] Устранение двусмысленности между роутами: канон `/week` (календарь недели) и `/plans` (библиотека шаблонов); `/plan`, `/templates`, `/programs` → редиректы.
  * [x] Унификация структуры навигационных табов: общий конфиг `nav-links` + одинаковый affordance «Ещё» на mobile и desktop.

### Фаза 2: Улучшение опыта тренировок (Workout UX & Gym Usability)
> Сроки: Среднесрочная перспектива  
> Цель: Сделать проведение сессии в зале максимально комфортным и автономным.

* [ ] Интерактивный таймер отдыха (Rest Timer):
  * Автозапуск настраиваемого таймера после сохранения подхода.
  * Звуковой сигнал, вибрация (Web Vibration API) и фоновые push-уведомления по окончании отдыха.
  * Быстрые кнопки добавления/уменьшения времени (+30с, -15с).
* [ ] Калькуляторы и подсказки прогрессии:
  * Автоматический расчет 1ПМ (One Rep Max) по формулам Эпли / Бжицки при логировании подхода.
  * Интеллектуальная подсказка следующего рабочего веса на основе динамики предыдущих сессий.
* [ ] Полноценный PWA и автономность:
  * Service Worker с кешированием приложения для стабильной работы при потере сети в тренажерных залах в подвальных помещениях.
  * Манифест для бесшовной установки как нативное приложение (iOS / Android).
* [ ] Сложные тренировочные структуры:
  * Поддержка суперсетов, трисетов, дропсетов и круговых тренировок в структуре сессии.

### Фаза 3: Продвинутая аналитика и база знаний (Analytics & Media)
> Сроки: Среднесрочная / Долгосрочная перспектива  
> Цель: Углубление аналитики прогресса и использование видеоматериалов.
* [ ] Интеграция видео и техники упражнений:
  * Отображение видеороликов и таймкодов (модуль sources) непосредственно в карточке выполнения упражнения во время тренировки.
  * Заметки атлета по индивидуальной технике выполнения и настройке тренажеров (высота сиденья, хват).
* [ ] Глубокая аналитика тренировочного объема:
  * Распределение нагрузки и подходов по мышечным группам за период (неделя, месяц).
  * Графики корреляции массы тела с силовыми показателями.
  * Тепловая карта тренировочной активности (Activity Heatmap) за год.
  * Кеширование агрегатов статистики в Redis (`stats:{userId}:{тип}:{период}`) — на инфраструктуре из Фазы 1. Осознанно отложено до этой фазы: пока таблицы малы, а данные меняются каждые 30 секунд во время активной тренировки, выигрыш минимален, а инвалидация — лишняя сложность. Кешировать в первую очередь **завершённые** периоды (прошлые недели/месяцы, год для heatmap) как неизменяемые, с инвалидацией по завершению тренировки.
* [ ] Импорт / Экспорт данных:
  * Экспорт всей истории в CSV/JSON.
  * Импорт истории тренировок из популярных приложений (Strong, Hevy, FitNotes).
* [ ] Надежный оффлайн-движок синхронизации:
  * Переход на IndexedDB (Dexie / RxDB) с поддержкой очереди транзакций и версионирования для надежного авто-мерджа без потери данных.

### Фаза 4: Экосистема, шеринг и интеграции (Scale & Ecosystem)
> Сроки: Долгосрочная перспектива  
> Цель: Создание платформы взаимодействия атлетов и тренеров.

* [ ] Шеринг программ и шаблонов:
  * Генерация публичных ссылок/QR-кодов для шаринга программ тренировок.
  * Каталог проверенных готовых программ (Starting Strength, PPL, Верх/Низ, 5/3/1).
* [ ] Кабинет тренера (Coach Dashboard):
  * Назначение программ подопечным, мониторинг выполнения и комментарии к подходам.
* [ ] Интеграция с носимыми устройствами:
  * Интеграция с Apple HealthKit / Google Health Connect (синхронизация веса, пульса и сожженных калорий).
* [ ] Быстрый голосовой ввод:
  * Поддержка распознавания голосовых команд для логирования («Жим 90 на 8»).
