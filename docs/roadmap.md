# Дорожная карта развития (Roadmap) IronLog

В данном документе представлены стратегические направления и сценарии развития веб-трекера тренировок IronLog.

---

## 🎯 Сценарии развития (Векторы)

В зависимости от бизнес-целей и потребностей пользователей проект может развиваться по 4 основным направлениям:

1. Gym-First (Фокус на удобстве в зале): максимальное ускорение ввода данных с мобильных устройств, таймеры, вибро-отклики, PWA, минимизация отвлекающих факторов.
2. Coaching & Social (Фокус на тренерах и сообществе): связь «тренер — ученик», шеринг программ и тренировок по ссылкам, комментарии, видеоразборы.
3. Data & Progression (Фокус на научном подходе и аналитике): периодизация, расчеты 1RM, отслеживание RPE/RIR, умные рекомендации весов, графики мышечных объемов.
4. Enterprise & Platform (Фокус на масштабируемости и безопасности): полноценная мультиюзерная изоляция данных, интеграция с фитнес-трекерами (Apple Health, Garmin), масштабируемый бэкенд.

## 🗺 Комплексный поэтапный план (Phased Roadmap)



### Фаза 1: Фундамент, безопасность и стабилизация (Core & Security)

> Сроки: Краткосрочная перспектива  
> Цель: Устранить технический долг, защитить пользовательские данные и улучшить базовую навигацию.

- [x] Безопасная аутентификация по постоянному коду (без SMTP):
  - [x] Хранение только bcrypt-хеша login-кода в БД (`login_code_hash`); plaintext в БД и логах не допускается.
  - [x] Схема поиска: колонка-индекс `login_code_lookup` = HMAC-SHA256(`LOGIN_CODE_PEPPER`, code) + bcrypt для проверки. Длина кода 12.
  - [x] Админ-панель (`/admin/users`, пункт в «Ещё» только для admin): список `email | создан | последний вход` **без** кода; создание пользователя и сброс кода с одноразовым показом plaintext.
  - [x] `POST /auth/register` для нового аккаунта возвращает код **один раз** в ответе API; повторная регистрация существующего email код не раскрывает.
  - [x] Rate-limiting: по IP на login/register + по аккаунту на login (5 / 15 мин после HMAC-lookup).
  - [x] Инвалидация сессий при сбросе кода: Redis-cutoff + durable `sessions_revoked_at` в БД.
- [x] Строгая мультитенантность и изоляция данных (Data Isolation):
  - [x] Проверка всех модулей бэкенда (sources, exercises, templates, body-measurement, feedback).
  - [x] Разделение упражнений на «системные» (общие) и «пользовательские» (кастомные).
  - [x] Гарантия фильтрации по userId во всех SQL-запросах.
- [x] Инфраструктура разделяемого состояния (Redis):
  - [x] Сервис `redis:7-alpine` в `docker-compose.yml`; данные не персистентные (`--save ''`, `appendonly no`), `maxmemory` + `allkeys-lru`, бэкапы не требуются. `depends_on` намеренно `service_started`, а не `service_healthy` — Redis не должен блокировать деплой.
  - [x] Порт `CachePort` в `shared/cache/core/ports` + `RedisCacheAdapter` / `MemoryCacheAdapter` в `infrastructure`.
  - [x] **Graceful degradation**: при недоступности Redis адаптер переключается на in-memory, приложение не отдаёт 5xx. `increment` работает и в fallback — иначе rate-limiting молча открылся бы. Текущее состояние видно в `GET /api/health` (`cache: redis | memory-fallback`).
  - [x] Кеш профиля пользователя в `AuthGuard` (`auth:user:{id}`, TTL 300 с) — снимает `SELECT` пользователя с **каждого** авторизованного запроса. Login-код в кеш не попадает.
  - [x] Отзыв JWT: по одному токену (логаут) и сразу по всем сессиям пользователя через отсечку по `iat` — основа для инвалидации при сбросе кода.
  - [x] Rate-limiting по IP через `@RateLimit` + `RateLimitGuard` (`/auth/login` — 10/15 мин, `/auth/register` — 5/час), с `trust proxy` в `main.ts`. Устойчив к перезапуску контейнера при деплое.
  - [x] Прогрессивная блокировка **по аккаунту** на login (`rl:auth-login-user:{id}`, 5 / 15 мин) — после HMAC-lookup, до bcrypt-verify.
  - [x] Задел на горизонтальное масштабирование (сценарий 4 «Enterprise & Platform»), где общее хранилище становится обязательным.
- [x] Оптимизация навигации и роутинга:
  - [x] Устранение двусмысленности между роутами: канон `/week` (календарь недели) и `/plans` (библиотека шаблонов); `/plan`, `/templates`, `/programs` → редиректы.
  - [x] Унификация структуры навигационных табов: общий конфиг `nav-links` + одинаковый affordance «Ещё» на mobile и desktop.
- [x] Баг: клиентский кеш/состояние после смены пользователя:
  - Симптом: после логина под другим аккаунтом (или после logout → login) UI/стор/localStorage иногда показывают данные предыдущего пользователя (тренировки, упражнения, планы и т.п.).
  - Причина (гипотеза): Zustand-сторы и локальный кеш (`localData` / pending sync / persist) не привязаны к `userId` и не сбрасываются на границе сессии.
  - Решение:
    - На `login` / `logout` / `switchMode` / `setCloudSession` — полный reset клиентских сторов (exercises, trainings, templates, session-related UI) и очистка user-scoped ключей в `localStorage` / IndexedDB (если появится).
    - Ключи локальных данных и persist-middleware scoped по `userId` (или `local` vs `cloud:{userId}`), чтобы данные разных аккаунтов на одном устройстве не пересекались.
    - После смены пользователя — принудительный refetch актуальных списков с сервера; не гидрировать UI из «чужого» кеша.
    - Регрессионный сценарий: User A → данные → logout → User B → только данные B; refresh страницы не возвращает A.
- [x] Автотесты (backend + frontend) — базовая инфраструктура и первые тесты:
  - **Backend (NestJS):** Jest + `@nestjs/testing`; unit-тесты: `exercise-group`, `generate-auth-code`, `LoginUseCase`, `CreateTrainingExerciseGroupUseCase`, sync whitelist DTO. Дальше: integration/e2e на HTTP API с тестовой БД.
  - **Frontend (Next.js):** Vitest + React Testing Library — utils (storage-scope, sync-meta, session-weight, groups, rest timer, drops) + `TrainingStatusBadge`. e2e (Playwright): smoke login/offline.
  - CI: `.github/workflows/test.yml` — `test` на каждый PR (backend unit + frontend unit + e2e smoke).
  - Приоритет покрытия: изоляция пользователей ✓, exercise groups ✓, sync payload whitelist ✓, session flow (rest timer, drops) ✓ — unit; e2e сценарии login/неделя/сессия/sync — следующий шаг.

### Фаза 2: Улучшение опыта тренировок (Workout UX & Gym Usability)

> Сроки: Среднесрочная перспектива  
> Цель: Сделать проведение сессии в зале максимально комфортным и автономным.

- [x] Интерактивный таймер отдыха (Rest Timer):
  - Автозапуск настраиваемого таймера после сохранения подхода.
  - Звуковой сигнал, вибрация (Web Vibration API) и фоновые push-уведомления по окончании отдыха.
  - Быстрые кнопки добавления/уменьшения времени (+30с, -15с).
  - Кастомизация в настройках: время по умолчанию, автозапуск, пропуск разминки, звук/вибрация/уведомления; per-exercise `restSeconds`.
- [x] Полноценный PWA и автономность:
  - Service Worker с кешированием приложения для стабильной работы при потере сети в тренажерных залах в подвальных помещениях.
  - Манифест для бесшовной установки как нативное приложение (iOS / Android).
  - Публикация в Store и полностью нативные клиенты: см. [docs/native-apps.md](./native-apps.md) (TWA, Android Studio, Jetpack Compose, Flutter, SwiftUI).
  - REST API, auth и офлайн-sync для локальных клиентов: [docs/native-integration.md](./native-integration.md).
- [x] Сложные тренировочные структуры:
  - Поддержка суперсетов, трисетов, дропсетов и круговых тренировок в структуре сессии.
- [x] Настройка отдыха между суперсетом / кругом:
  - `group.restSeconds` задаётся в карточке шаблона и в сессии тренировки; таймер после пары/круга берёт отдых группы, иначе per-exercise / дефолт.
- [x] Баг: разъединение суперсета не применяется (как будто только локально):
  - `deleteGroup` уходит в delete-outbox (`training-group` / `template-group`) и удаляется на сервере до повторного upsert.
- [x] Баг: дублирование упражнений в тренировке:
  - Копирование из шаблона не повторяется, если упражнения уже есть; зеркало с облака заменяет состав, а не склеивает; heal снимает дубли по `exerciseId + order`.
- [x] Плавные переходы между вкладками:
  - Crossfade контента при смене основных табов (Сегодня, Неделя, Статистика, Ещё) через View Transitions API.
  - Sidebar/header остаётся неподвижным во время анимации; scroll-to-top при смене таба.
  - Skeleton при подгрузке данных (TabPageFallback): без скачков layout и «пустых» кадров на cold cache и во время запросов.
  - Стабильный контент-слот (`min-height: 100dvh − nav`): crossfade без схлопывания `main` при разной высоте страниц; без morph height в View Transition.
  - Stale-while-revalidate в stores: при повторном заходе на вкладку показывать кеш, обновлять в фоне.
  - Без анимации на /login, /~offline и fullscreen-сессии (/trainings/[id]).
  - prefers-reduced-motion: мгновенная смена без анимации.

### Фаза 3: Продвинутая аналитика и база знаний (Analytics & Media)

> Сроки: Среднесрочная / Долгосрочная перспектива  
> Цель: Углубление аналитики прогресса и использование видеоматериалов.

- [x] Интеграция видео и техники упражнений:
  - Отображение видеороликов и таймкодов (модуль sources) непосредственно в карточке выполнения упражнения во время тренировки.
  - Заметки атлета по индивидуальной технике выполнения и настройке тренажеров (высота сиденья, хват). (форум?)
- [x] Глубокая аналитика тренировочного объема:
  - [x] Распределение нагрузки и подходов по мышечным группам за период (неделя, месяц). Диаграмма тела + бары; переключатель неделя/месяц/год.
  - [x] Графики корреляции массы тела с силовыми показателями.
  - [x] Тепловая карта тренировочной активности (Activity Heatmap) за год.
  - [x] Кеширование агрегатов статистики в Redis (`stats:{userId}:{gen}:{тип}:{период}`) — завершённые периоды, инвалидация по `gen` при завершении тренировки.
- [x] Коэффициенты мышечных групп в упражнениях:
  - Сейчас объём делится поровну между всеми указанными группами (`1 / N`).
  - В карточке упражнения: основная группа — коэффициент **1**, дополнительные — **0.6** (можно несколько дополнительных).
  - Аналитика объёма и диаграмма тела считают вклад с этими весами; миграция существующих упражнений (первая группа = основная).
- [x] Импорт / Экспорт данных:
  - Экспорт всей истории в CSV/JSON.
  - Импорт истории тренировок из популярных приложений (Strong, Hevy, FitNotes).
- [x] Надежный оффлайн-движок синхронизации:
  - IndexedDB (Dexie): очередь транзакций (WAL) + ревизии записей (`rev` / `syncedRev`) для авто-мерджа без затирания локальных правок; миграция с localStorage.

### Фаза 4: Экосистема, шеринг и интеграции (Scale & Ecosystem)

> Сроки: Долгосрочная перспектива  
> Цель: Создание платформы взаимодействия атлетов и тренеров.

- [ ] Шеринг программ и шаблонов:
  - Генерация публичных ссылок/QR-кодов для шаринга программ тренировок.
  - Каталог проверенных готовых программ (Starting Strength, PPL, Верх/Низ, 5/3/1).
- [ ] Кабинет тренера (Coach Dashboard):
  - Назначение программ подопечным, мониторинг выполнения и комментарии к подходам.
- [x] Выгрузка системного каталога для seed:
  - Колонка `is_system` отделяет общий каталог от пользовательских упражнений.
  - Админ скачивает zip (`exercises.json` + главное изображение) с `/admin/catalog` и может импортировать его на другом окружении.
  - Дубли по id и нормализованному названию в сид не попадают (insert-only).
  - Пользовательский JSON-бэкап не включает системные упражнения.
- [x] Новости платформы в «Ещё»:
  - Лента `/news` и карточка `/news/[slug]`; пункт в «Ещё» и админка `/admin/news`.
  - Контент в Postgres (`news`: slug, title, excerpt, jsonb-секции, `published_at`); чтение `GET /news` без JWT (локальный режим при наличии сети).
  - Админ создаёт, правит и удаляет новости; секции — заголовок + абзацы или список, без markdown.
  - Первая запись сидится миграцией: «Что можно делать в IronLog». Офлайн — empty «Нет сети, новости недоступны».
- [x] Баг: на телефоне «всё синхронизировано», на другом устройстве данных нет (пока не зайти в Статистику):
  - Симптом: устройство A пишет «Все локальные данные синхронизированы»; устройство B не видит новую/обновлённую тренировку на Сегодня/Неделе. Часто появляется только после вкладки «Статистика». Гипотеза пользователя: локальный кеш перетирает более новые облачные данные.
  - Причина:
    - «Синхронизировано» = пустая очередь **отправки** (`pending` trainings/templates/catalog). Это не pull и не подтверждение, что другое устройство получило снимок.
    - Фоновый sync только **push** (`requestBackgroundSync` / `visibilitychange` / `online`). С сервера детали подтягиваются точечно (`fetchOne` / `GET /stats/*`), а не при открытии приложения.
    - `fetchList` для уже известных id **не обновляет** локальные упражнения/сеты; для новых id кладёт **пустой shell** со статусом `synced`. Неделя фильтрует `from`/`to` по локальному каталогу; при таймауте списка (4 с, если каталог уже есть) ошибка глотается — остаётся старый локальный список.
    - Статистика обходит это: агрегаты идут с сервера (`/stats/volume` и т.п.), плюс `fetchList({ limit: 100 })` без недельного окна — после успешного ответа новые shell попадают в локальный каталог, и остальные вкладки начинают их видеть.
    - Локальное может затереть облако: пустой shell + неуспешный/медленный `GET` → `hydrateFromTemplate` копирует план без подходов → `pending` → background push last-write-wins (`pushTrainingSnapshot` без `rev`). `shouldKeepLocalOverRemote` сравнивает только число сетов/упражнений, не свежесть.
  - Решение:
    - Pull при фокусе приложения (не только push): список с сервера + для изменившихся записей детали; не помечать list-shell как `synced`.
    - Не гидрировать из шаблона и не пушить, пока не получен облачный снимок (или явный 404). Пустой/шаблонный локальный снимок не должен побеждать remote с подходами.
    - Мердж по `rev` / `updatedAt` (задел фазы 3 IndexedDB), а не «кто последний upsert-нул».
    - Регрессия: A завершает тренировку → «синхронизировано» → B открывает Сегодня/Неделю (без Статистики) и видит ту же сессию с подходами; повторный заход B не затирает подходы A пустым планом.
- [x] Баг: поиск в каталоге упражнений ломает отображение в тренировке (и в шаблоне):
  - Симптом: после поиска на `/exercises` в сессии имена становятся обрезанными id, пропадают картинка и диаграмма мышц. Состав тренировки на месте.
  - Причина: `useExerciseStore.items` — и каталог, и результаты поиска. `fetchList()` без аргумента повторно фильтрует по leftover `query`. Сессия и шаблон резолвят имя/медиа через `items.find`.
  - Решение: `items` всегда полный каталог; поиск только в UI `/exercises`; `query` не режет стор; сброс `query` при смене пользователя.
  - Регрессия: поиск «жим» → открыть тренировку с приседанием → полное имя и медиа; возврат в каталог — строка поиска на месте.
- [x] Оптимизация фото упражнений на слабой сети:
  - Симптом: в зале (подвал, 2G / save-data) каталог и сессия долго ждут или показывают битые картинки; диаграмма мышц при этом есть.
  - Причина:
    - Upload-service пишет файл как есть (до 5 МБ) в `/upload/{uuid}.ext`; карточка ~300px и сессия получают полный оригинал. `next/image` не используется.
    - На `/exercises` сетка рендерит все карточки сразу — до ~200 параллельных запросов после catalog sync; нет `loading="lazy"` / `decoding="async"`.
    - Нет thumb/md вариантов и `srcset`; nginx `/upload/` без `Cache-Control`.
    - SW кеширует картинки только через дефолт Serwist (SWR, 64 LRU) — не гарантирует каталог офлайн.
    - Нет `onError`-fallback: битая сеть = сломанный блок. Тумблер «скрыть фото» в сессии есть, режима экономии трафика нет.
  - Решение (слоями, без миграции на `next/image`):
    - Клиент: общий `ExerciseImage` — `loading="lazy"`, `decoding="async"`, `onError` → плейсхолдер или `MuscleDiagram`.
    - Доставка: `Cache-Control: public, max-age=31536000, immutable` на `/upload/` (UUID неизменяемый); в SW отдельный CacheFirst для `/upload/` с лимитом под каталог (~256).
    - Пайплайн: при загрузке sharp в upload-service — `{uuid}-thumb.webp` (~320w) и `{uuid}-md.webp` (~800w); карточка/сессия берут thumb, деталь — md; `srcset`.
    - Офлайн/зал: после catalog sync префетч thumb (`primaryImageThumbUrl`) в SW/браузерный кеш; на `saveData` / `slow-2g` сессия не грузит фото (тумблер остаётся, описание предупреждает).
  - Регрессия: каталог на медленной сети показывает карточки без блокировки сетки; в сессии офлайн — диаграмма или закешированный thumb, не broken-image; повторный визит не качает 5 МБ оригинал.

## 📊 Матрица приоритетов (Impact vs Effort)


| Задача                                                        | Ценность (Impact) | Трудоемкость (Effort) | Приоритет                         |
| ------------------------------------------------------------- | ----------------- | --------------------- | --------------------------------- |
| Автотесты backend (Jest, use-case + API)                      | Высокая           | Средняя               | P0 (фундамент стабильности)       |
| Автотесты frontend (Vitest)              | Высокая           | Средняя               | P0 (регрессии UX и sync)          |
| Таймер отдыха с уведомлением                                  | Высокая           | Низкая                | P0 (Ближайший спринт)             |
